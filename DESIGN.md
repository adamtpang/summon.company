# Summon Design Principles

**Status:** v1.2 - the source of truth for a beautiful, ruthlessly minimal AI-agent command center. Governs both structure AND intentionality. Full research + evidence: `doc/research/AGENT-COMMAND-CENTER-DESIGN.md` (Sequoia agent thesis, peer command centers, the design canon), `doc/research/BEST-DASHBOARDS.md` (the Dashboard grid), `doc/research/DESKTOP-UX-SKELETONS.md` (the IA). Brand token VALUES live only in `ui/src/index.css`; nothing in `ui/` hardcodes them.

Changes in v1.1 (board direction, 2026-09-01): Shapeable's owner-feedback system reconciles the earlier monochrome ruling into an institutional ink-and-ice palette. Near-navy ink remains business truth, pale ice replaces stark white as the reading field, and Summon Blue is a scarce decision and focus signal. Governed status hues still mean data only. This change aligns the authenticated product with the public product family without adding ornamental gradients, luxury theater, or card chrome. Earlier rulings remain historical evidence below where they do not conflict with v1.1.

## What this document is for

Agents and humans modifying `ui/` treat this file as the source of truth for design decisions. **The intentionality gate (below) is binding:** every on-screen element must trace to a reason here. Storybook is the verification surface - it documents the system; it does not define it. If a change conflicts with this document, change this document first (with review) or change the code.

## The thesis (the one question)

Summon is a command center for a founder supervising AI employees. It answers ONE question first, above all others: **which of my agents needs me right now.** Every element either sharpens that answer or is deleted. Three surfaces, nothing more: **Dashboard** (the glance - which employees need me, what's the company's state), **Chat** (talk to any employee, WhatsApp-simple, outcomes not logs), **Decisions** (the drainable queue of what needs my yes). Beauty here is not decoration - it is the absence of everything that isn't that answer. The canon and the Sequoia peer set agree: the defining design decision is almost always a *subtraction*.

## The thirteen laws (enforceable; each element must pass all)

1. **Deletion test.** Every element must survive a deletion attempt - if removing it loses no data and no affordance, DELETE it (don't shrink it). Log the removal in the PR.
2. **Intentionality gate.** Every on-screen element traces to a DESIGN.md entry; every entry states its REASON + the trade-off it settles + the alternative rejected. No trade-off = no decision = no bespoke element.
3. **One primary action per surface.** Only one element carries primary visual weight (size + placement + weight). Demote or delete every competing CTA.
4. **Ink, ice, and one scarce signal.** The application uses near-navy ink for business truth, pale ice for the reading field, and Summon Blue only for the primary decision, selected state, or visible focus. Blue may also encode measured data when its label makes that role explicit. Positive green, warning ochre, and destructive red remain governed statuses and are never decorative. Agent-capsule colors stay contained to agent identity. *Reason:* pure black and white made the public and authenticated products feel unrelated and gave focus no proprietary signal; a restrained institutional palette feels finished without becoming ornamental. *Alternative rejected:* gradient SaaS chrome, gold-on-black luxury styling, decorative blue washes, or multiple competing accents.
5. **Status color is semantic and never alone.** Pair every green/amber/red with an icon or label. Never red/green decoratively.
6. **Every metric earns its place** with trend + delta-vs-target + a next step. A lone big number gets context or gets cut.
7. **Hierarchy from type + space first.** A border/box ships only if meaning is still lost after spacing and weight are set. Draw kept borders as a 1px shadow, not a line.
8. **One type system, roles by meaning.** The default application uses one sans family with roles expressed by size, weight, and case. Mission Control's documented Polsia-inspired live board is the sole exception: an editorial serif represents company facts and a console mono represents machine state, timestamps, identifiers, and commands. The contrast must encode human-readable business versus machine operation, never decoration. Few weights. No chips/boxes merely to signal role.
9. **Double the whitespace.** Take the spacing that feels like enough, then double it. Every gap is a multiple of one base unit; repeated data is the same component at the same scale.
10. **No spinners on the home screen.** Cache all console state locally, stream the event log in the background, keep every hop < 100ms. Speed is a design decision.
11. **Motion is sub-100ms, GPU-only.** Interface state changes animate transform/opacity in under 100ms, never layout (width/height/top). The contained company-world simulation is the sole timing exception: representational work/idle/walking motion may run long enough to be legible, but still uses transform/opacity only, never blocks the underlying action, and becomes static under reduced-motion.
12. **Five-second test, two levels max.** Any screen: identify the primary signal, tell good from bad, know if action is needed - in five seconds. Disclosure caps at two levels; a third level means the structure is wrong.
13. **Glass signals elevation, never data.** Translucent/blurred surfaces are permitted ONLY where something floats above the context it came from and is dismissible: the Cmd-K palette, modals/dialogs, sheets, dropdown menus, popovers, the Decisions deck card, toasts. They are forbidden on Dashboard data zones, tables, metrics, status, and any number the board reads to make a call. **The recipe (implemented 2026-07-18, `ui/src/components/ui/`):** surface = `bg-(--glass-surface) backdrop-blur-xl border-(--glass-border)`; the dimming overlay behind modal surfaces = `bg-black/40 backdrop-blur-sm`; tokens live in index.css (`--glass-surface` = white 62% / near-black 55%, `--glass-border` = ink 10% / paper 12%). Children of a glass surface never paint their own opaque background (the ⌘K palette's inner Command is `bg-transparent` for exactly this reason). Tooltips stay opaque - too small for blur to read as anything but haze. *Reason:* glass carries exactly one honest meaning - "this is transient and sits above what you were doing" - which is a real affordance the flat system otherwise spends a border on (law 7), so used here it ADDS signal rather than decoration. *Trade-off it settles:* it buys that depth cue at the cost of text contrast and of compositing during scroll; we pay that only where content is transient, short, and recoverable by dismissing it - never where law 12 or a metric's legibility is at stake. *Alternative rejected:* glass as a global skin across every card and panel. It lowers contrast on precisely the dense data the console exists to show, it competes with the single accent (law 4), and by making every surface equally shiny it flattens hierarchy - the opposite of what a command center is for. Board ruling 2026-07-17: the look is wanted; this law is where it is allowed to live.

## The intentionality gate (how "everything has a reason" is enforced)

An element ships to `ui/` only if it can point to a law it serves OR a DESIGN.md entry that records: *what it is · the reason it exists · the trade-off that reason settles · the alternative that was rejected.* "It looked empty" and "just in case" are not reasons. A PR that adds a surface, a nav item, a card, a badge, or a CTA without that trace fails review. This is the Google design-doc discipline (Malte Ubl): the decision and its rejected alternatives are written down BEFORE the pixels, so the interface stays legible to the next agent and stays honest over time.

## Product stance

Summon is an AI-agent company command center. The user is the BOARD, scanning which employees need them and deciding. Every screen answers, in order: *which agent needs me, what's the company state, what do I do about it.* Density serves scanning - but density comes from information, never from chrome.

### Mission Control composition

**What it is:** a Polsia-inspired live company newspaper adapted to Summon's evidence model: one ink console strip, a restrained company masthead, governed blue/green live-state semantics, and a responsive editorial board of company, tasks, office, outcomes, and systems. The visual hierarchy is flat and legible: serif company facts, mono operational metadata, thin ink section rules, square two-pixel controls, and almost no card chrome. The digital office remains Summon's differentiator and carries real agent/task state rather than Polsia's aggregate public feed. Existing shadcn primitives remain underneath actions, dialogs, and accessibility behavior even when the surface treatment is quieter.

**Source and evidence:** [Polsia homepage](https://polsia.com), [Polsia Live](https://polsia.com/live), and [Polsia login](https://polsia.com/login), captured 2026-08-26 with live branding/markdown scrapes, desktop screenshots, a 390px screenshot, and computed-style measurements. The live dashboard screenshot is the primary product reference:

![Polsia Live product reference](./.firecrawl/polsia-live-2026-08-26.png)

Observed values: Editorial New with Times New Roman fallback for company content; Suisse Mono with Courier fallback for commands; 16px desktop and 14px mobile section headings; 320px desktop columns with 30px gutters; 20px page insets; 1px black section rules; 2px action radius; 12px uppercase mono actions with 0.48px tracking; white canvas; black ink; orange reserved for live work. Proprietary Polsia font files, logo, photography, copy, ASCII mascot, and brand name are not copied. Summon uses locally available editorial and console fallbacks and its own identity, agents, data, and language.

**Reason:** the dashboard must feel like a company visibly operating, not a generic SaaS analytics product. Polsia achieves that through typography, evidence density, and visible output rather than ornamental cards. This makes the business simulation credible while preserving Summon's stronger control, governance, and ownership model.

**Trade-off settled:** editorial density replaces generous card padding, the desktop board favors three readable columns over equal-width metric tiles, and mobile becomes a deliberate single-column feed. The page may feel less conventionally “app-like,” but it becomes more distinctive and faster to scan. Shadcn remains the behavioral substrate rather than the visual personality.

**Alternative rejected:** continuing to polish the prior shadcn dashboard grid. It was technically tidy but still looked interchangeable with every modern admin panel and kept giving empty integrations the same weight as live company work.

#### Authenticated company-workspace reference

**Primary reference:** the authenticated Polsia company dashboard at `https://polsia.com/dashboard/anchor-7`, inspected read-only on 2026-08-27 after the anonymous Firecrawl request correctly redirected to login. Firecrawl supplied the public design tokens, help-center product model, and page inventory; the authenticated browser supplied the rendered DOM, computed styles, desktop/mobile behavior, and the screenshot below.

![Authenticated Polsia company dashboard reference](./.firecrawl/polsia-dashboard-anchor-7-authenticated-2026-08-27.png)

**What changes from the public `/live` reference:** Mission Control is a fullscreen company workspace, not a dashboard inside permanent application navigation. A black machine-event strip spans the top. Beneath it, one quiet company bar carries only the company identity, one create action, and one menu. The operating surface is a masonry-like set of fixed-width company widgets — company state, tasks, routines, website, social, email, documents, team, ads, media, business — beside a persistent board-chat rail. Navigation, configuration, and infrequent controls stay behind the menu or within the relevant widget. On a phone the widgets become one deliberate sequence and chat becomes a fullscreen drawer.

**Observed desktop measurements:** white canvas and black ink; Editorial New / Times New Roman at 16px and 24px line-height for facts; Suisse Mono / Courier New at 11–12px with roughly 0.44–0.48px tracking for controls and metadata; 8px workspace inset; approximately 363px widget columns with 10px gutters; approximately 380px chat rail; 1px black section rules; 2px global-control radius; task cards with a light-gray fill, 4px radius, 1px black border, and 1px hard shadow. The measured 1,897px viewport fit four operating columns plus chat. Values are adapted through Summon's token layer, never copied as raw component values.

**Summon translation:** preserve the same visual compression and information architecture while keeping Summon's stronger truth model. The company-status widget contains the real nine-department office. Tasks retain accountable owners, tier, execution state, and board decisions rather than spending credits. Website, Payments, Social, Outreach, Inbox, Ads, Stack, documents, outcomes, and routines remain separate causal widgets. The right rail embeds the real board chat. Live orange still means active work only. Proprietary Polsia fonts, mascot, copy, logos, customer data, pricing, and hosted infrastructure claims are not copied.

**Hard layout rules:** no permanent left sidebar or breadcrumb chrome on Mission Control; no hero title; no generic metric-card row; no equal-height card grid; no decorative gradients; no radius above the small control/task-card tokens; no chat duplication. Desktop is company bar → operating columns + chat. Mobile is company bar → one ordered operating feed, with chat opened explicitly as a fullscreen surface. Every widget either exposes current evidence or a direct route to the owning control surface.

**Application navigation:** outside the fullscreen Mission Control and Factory Floor workspaces, the permanent ink-and-ice rail is a Summon company switcher and context surface, not a feature catalog. It is Ice in light mode and Ink in dark mode. Its primary set is Fleet, Mission Control, Company Office, Diagnose Codebase, Tasks, and Decisions; the only standing administration exits are Org, Costs, and Settings. Search remains the route to infrequent tools and extensions remain discoverable without restoring Paperclip's Projects/Agents/Chat/Messages/Inbox/Audit/Watchtower/Roadmap/Activity inventory to first-level navigation. The rail carries the Summon mark, one selected company, one primary task action, and the minimum navigation needed to answer what the board should do next. Mobile preserves the same model as Control, Office, Create, Tasks, and Decide. Removing a link never deletes its route or its evidence contract.

#### Company-control workspace

**What it is:** the compact Routines widget opens one transient Company controls workspace above the dashboard context. Running state and the kill switch lead; Decide, Nightshift, and Brief scan as three columns on a wide screen and one ordered column on a phone; the dispatch rail follows at full width. The underlying newspaper columns and persistent board chat do not reflow.

**Reason:** autonomous execution is infrequent but consequential. It needs enough width to show decision, duration, dollar ceiling, evidence, and queue order together without turning one 363px company widget into a page-length form or leaving the rest of Mission Control visually empty.

**Trade-off settled:** opening the controls temporarily obscures part of the live company, but preserves spatial context through the dismissible glass surface and keeps the dashboard dense when the controls are closed. The mobile surface scrolls internally so the company page never gains horizontal overflow.

**Alternative rejected:** expanding Company Loop inside the Routines column. At the authenticated-reference desktop width it stacked the three steps into a narrow rail and left most of the operating workspace blank, hiding the relationship between the decision, the bounded run, and its receipt.

#### Live company-world direction

**What it is:** the Factory Floor island is a contained business-simulation view of the real control plane. It owns the exact available viewport instead of sitting inside Paperclip navigation or a scrolling dashboard; the ranked queue remains one explicit in-world drawer. That drawer uses the same company-office vocabulary as the map—Boardroom, department work areas, active tasks, awaiting review, and retained evidence—rather than switching into a restaurant metaphor or linking back to the classic Inbox. Each visible villager is one real approved employee. An open role keeps its house and department label but never invents a ghost worker; a seeded Core-8 seat awaiting the board remains inspectable as `Pending approval` but is neither drawn as hired nor messageable. The villager's nametag, activity tell, current goal, day/night state, and slim fixed detail card derive from the same employee, task, and live-run records used elsewhere. The card is deliberately hard to vary: profile image, name, title, a deterministic goal of at most three words, and one last-role chip. It never repeats the room, state, task ID, events per minute, counts, bytes, transcript snippets, or tool names. Every approved employee has a visible work spot. Idle, queued, paused, and long-quiet villagers remain by the house; only a genuinely live task moves the same villager to the work spot with a stepped transform and runs the work animation there. Reduced motion removes travel and bobbing without changing the underlying state. A paused employee visibly sleeps; an available or waiting employee sleeps only after a real `lastHeartbeatAt` is at least one hour old. Missing history remains merely quiet, and live `tool`, `assistant`, or initiating-user activity overrides sleep. No tool name or transcript snippet appears on the map or card. A single-line work radio floats at the middle-bottom of the map without shifting the scene; the plot grid reserves a prompt-safe area so all nine houses, names, and states remain visible at desktop and phone sizes. Selecting a staffed villager with non-terminal current work enables it; the first villager click produces a tiny gesture-bound sound unless the board has pressed `M`, and no autoplay context exists before that click. Enter clears immediately, wakes a sleeping target in the local scene, moves the non-art `you` marker toward that employee, shows a short player-only speech clip, gives the villager a user-message reaction, and posts the complete instruction as a durable comment on that exact task. Before send, the HUD says that the action may wake the employee and use provider budget. Empty roles, pending seats, employees without active work, and shipped/cancelled tasks remain disabled; completed work can only be deliberately followed up from the task surface. Delivery failure stays visible and never reverses the optimistic movement or wake. Only the exact `you` nametag renders until the board chooses the final player look.

**Reason:** the office should not merely visualize a company; it should make the founder feel present inside a real one. Attaching direction to accountable work preserves Summon's task/comment audit trail while giving the simulation one immediate, comprehensible action.

**Trade-off settled:** conversation is intentionally narrower than a free-form employee inbox. The founder can direct what the employee is currently accountable for without creating a second transcript system, but must open or assign work before starting a new topic. The 650ms walk is a contained representational exception to law 11; the task post runs in the background and reduced-motion removes the transition.

**Alternative rejected:** wiring the HUD to the local-only Messages prototype, creating an unaudited chat transcript, silently reopening finished work, or invoking an agent directly without a work object. Those paths respectively fake persistence, split company memory, revive completed work accidentally, or spend authority without an accountable task.

### Company chat input surface

**What it is:** one quiet composer for accountable company direction. Text remains the default. Choosing a file is an explicit mutation: it prepares the standing `Board Operations` issue only when needed, stages the file in the company-owned issue attachment store, shows upload/error/attached state, permits removal, and carries only validated attachment IDs into the next Cofounder turn. Filenames and contents are untrusted evidence; the configured employee receives them through the normal issue context and no cross-company reference is accepted. Sending records one board comment and wakes the opinionated company Cofounder through the governed provider-neutral heartbeat runtime; the browser stream only observes that run. Missing or non-invokable employees fail closed, and leaving the page never cancels accepted company work. Voice is a separately governed draft path: the browser asks for microphone permission only after the board presses the mic, records for at most the board-set 15–120 second ceiling, and submits one bounded audio file through the company-owned AI gateway. Summon reserves a fixed maximum request amount against a separate monthly micro-dollar ceiling, records only model/usage/cost/status metadata, zeroes the server audio buffer, returns the transcript only to the browser composer, and never sends it automatically. **Reason:** text, files, and microphone input must extend the same audited company memory and employee governance without creating a second chat, transcript store, identity, or model executor. **Trade-off settled:** a new company shows both input actions before any conversation exists, but viewing Chat alone creates nothing; unavailable voice or Cofounder execution names the exact gateway, budget, staffing, or runtime boundary. **Alternative rejected:** decorative controls, a hardcoded shell model, browser-owned opaque speech recognition, automatic upload on page view, persisted raw audio or draft transcripts, automatic transcript send, embedding raw file bytes in a parallel prompt, or relabeling historical concierge output as employee work.

### Company lifecycle surface

**What it is:** one Company Settings control that separates Pause, Archive, Restore, and permanent deletion. Pause stops new timer and scheduled admission while honestly allowing already-submitted provider work to settle. Archive additionally cancels queued or running Summon work, pauses employees, and hides the company without erasing it. Permanent deletion is available only after Pause or Archive, requires zero active runs and wake requests plus the exact typed company name, and states which company-owned external resources remain outside Summon's control. **Reason:** stopping automation, hiding a company, and erasing its control-plane record are materially different decisions; the board must see their reversibility and blast radius before acting. **Trade-off settled:** the destructive path takes an extra Pause/Archive step and exact-name confirmation, but the ordinary temporary stop remains one click and budget hard stops cannot be bypassed. **Alternative rejected:** one generic Delete button, a browser confirm, or pretending that deleting Summon state also cancels billing and deletes provider infrastructure. Those paths respectively collapse distinct intents, make irreversible loss too easy, or create a false safety claim.

### Company inbox surface

**What it is:** one company-level customer conversation queue with accountable source ownership, exact read/draft/send/work authority, fixed-origin Gmail sync, one exact governed Slack company channel, immutable approval correlation, explicit board submission, one canonical message-to-task bridge, and append-only receipts. A separately granted `notifications.send` capability turns the exact Slack channel into a durable board-alert destination for a seven-event allowlist; capture, reservation, success, definite failure, unknown outcome, and revocation remain inspectable. An inbound message can become one owned task; its live status projects back into the message while the task points to the canonical Inbox record instead of copying the body. Mission Control compresses the same truth into a Customer channels glance: governed sources, unread messages, open customer tasks, provider state, exact Slack channel label, and notification exceptions. **Reason:** “the company talks and works while I sleep” is only credible when the board can distinguish received, assigned, working, drafted, awaiting approval, reserved, sent, rejected, ambiguous, notified, and notification-failed work without exposing or copying a credential or customer body. **Trade-off settled:** the page places custody, provider receipts, and board-notification receipts beneath the three-pane conversation workflow. The notification rail reuses the heartbeat scheduler and authoritative activity instead of adding a second scheduler or scattering provider calls across business mutations. **Alternative rejected:** a chat-like composer that sends on save, a generic activity-to-Slack firehose, or copying every customer body into a task/alert. They respectively turn drafting into an external commitment, create spam and accidental disclosure, or create conflicting sources of customer truth.

### Company website surface

**What it is:** one provider-to-deployment-to-domain-to-health control chain with accountable authority and append-only receipts. The custom-domain panel shows Vercel's exact current access state and DNS recommendations beside one board-only configure/refresh action. A separate compact Background tasks section lists only provider-deployed application jobs—their route, UTC schedule, optional host, and disabled state—and labels them separate from Nightshift. It is read-only; source and approved deployment remain the mutation boundary. **Reason:** a domain or cron is not “connected” because an agent says so; the board needs to see the provider relationship, deployed definition, required DNS evidence, and resulting public health in one causal surface. **Trade-off settled:** the board may attach and verify an already-owned domain directly, while purchase, registrar access, DNS writes, cron mutation, manual job execution, and deletion remain separate governed capabilities. **Alternative rejected:** a magical one-click “launch,” a second Summon application scheduler, or a generic provider console embedded in Summon. They respectively spend authority the user did not grant, split deployment truth across two schedulers, or expose provider complexity without preserving Summon's evidence boundary.

### Company website deep-repair surface

**What it is:** one compact escalation lane inside Website control for a live production bug that a standard repair did not solve. The board links the failed/blocked/completed source task, records the affected page, reproduction clicks, expected and actual behavior, explains recurrence, accepts a fix-only boundary, and confirms one exact USD recorded-spend ceiling. Starting creates one high-priority ordinary task under the website owner, source goal, source workspace, normal artifact/evidence rules, and the central heartbeat budget gate; the active task and recorded spend remain visible on the same card. It prepares a reviewable repair and never authorizes deployment. **Reason:** a “try harder” button hides scope, cost, and whether the earlier repair taught the company anything. Root-cause escalation is credible only when it preserves the failed attempt as evidence, gives one employee room to investigate, and still stops new runs at an explicit liability. **Trade-off settled:** the form asks for more evidence than a normal task and the ceiling cannot retroactively stop a provider call already in flight; in return, the next run is blocked once recorded spend reaches the amount and the board sees the limitation before confirmation. Existing company, project, and employee hard stops remain stronger. **Alternative rejected:** a generic super-agent mode, automatic production deployment, proprietary refundable credits, or an unbounded retry loop. They respectively erase the repair/build distinction, collapse code evidence into external mutation, falsify provider cost, or turn persistence into open-ended spend.

### Company payments surface

**What it is:** one company-level Stripe control surface for custody, readiness, public offers, authenticated fulfillment, customer protection, recent provider evidence, and an append-only receipt trail, plus one compact Mission Control glance. Account, charges, payouts, and webhook fulfillment remain the causal readiness chain. A separate customer-protection panel binds an independently restricted key, shows bounded aggregate customers/refunds and redacted disputes, and lets the board refund one authenticated Summon checkout with explicit amount/reason confirmation. Ambiguous refunds expose one reconcile action and never a replay action. **Reason:** customer revenue is a first-class company outcome, but “paid” is not “delivered,” and “refunded” cannot be a hopeful local state. The board must see the path from company custody through authenticated payment to delivery or customer remedy without exposing identity, card data, or dispute evidence. **Trade-off settled:** two restricted credentials and webhook setup add provider ceremony, while containing public-offer authority, customer-protection authority, and inbound event authority in three exact boundaries. Customers collapse to counts; disputes collapse to fixed safe fields; the board goes to Stripe for sensitive evidence. **Alternative rejected:** one broad Stripe key, polling revenue as fulfillment, copying Stripe's customer/dispute objects, or retrying an uncertain refund. They respectively enlarge blast radius, lose causality, create a second customer-data store, or risk returning money twice.

### Company social surface

**What it is:** one company-level social publishing control for connected external identities, exact post destinations, scheduled and published work, provider receipts, and accountable authority, plus one compact Mission Control glance. **Reason:** a company speaking in public is both an operating outcome and a reputational act unless its exact words, destinations, owner, and external receipt remain inspectable. **Trade-off settled:** the page adds a domain drill-down, while recurring content generation stays in the existing Automations product and Mission Control carries only channel/queue/receipt counts. **Alternative rejected:** a second social-specific scheduler or a chat-only “post this” flow. The first duplicates durable routine machinery; the second hides the difference between a draft and an externally published claim.

### Company outreach surface

**What it is:** one company-level permission-based follow-up control for accountable sender authority, evidence-backed contacts, bounded campaigns, exact messages, global suppressions, replies, and provider receipts, plus one compact Mission Control glance. Every submitted email carries an opaque one-click stop capability whose raw value exists only in the provider request and recipient link; Summon retains its SHA-256 hash. The public confirmation is a standalone black-and-white editorial page with one action, no application chrome, no identity prompt, and no tracking. GET confirms but cannot mutate; POST creates the existing company-global suppression. Sender connection automatically provisions and verifies one authenticated Postmark event endpoint; the surface shows that readiness and requires reconnect for legacy or failed authority. Only delivery, hard bounce, and complaint events are admitted—open and click tracking remain off. **Reason:** outbound contact becomes legitimate only when the company can show why this person expects it, who owns the relationship, what exact message crossed the boundary, and whether a reply, bounce, complaint, or recipient-controlled opt-out stopped later work. **Trade-off settled:** the page exposes compliance evidence and suppression state beside commercial work, while recurring preparation remains in Automations and Mission Control carries only campaigns, eligible contacts, and suppressions. Recipient confirmation adds one deliberate click for body links so automated email scanners cannot opt people out; supporting RFC 8058 headers preserves true one-click behavior in compatible mail clients. Automatic webhook ceremony adds one provider verification step, but removes the dangerous state where a sender can submit while bounce and complaint evidence is disconnected. **Alternative rejected:** a generic cold-email sequencer, a chat-only “contact these leads” action, a GET link that mutates immediately, or a manually copied unauthenticated webhook. They respectively optimize volume before authority, hide recipient basis and stop conditions, let security scanners silently suppress real recipients, or make critical stop evidence optional.

### Company ads surface

**What it is:** one company-level paid-distribution control for external account custody, exact creative/audience/destination, bounded spend, provider state, performance evidence, and immediate stop authority, plus one compact Mission Control glance. **Reason:** advertising is simultaneously a public claim and a recurring external spend; the board must see the maximum liability and exact message before activation, then see spend and outcome together. **Trade-off settled:** the first surface deliberately supports one simple traffic campaign with broad adult geography and an existing Meta image asset, while advanced targeting, generation, experimentation, and attribution wait behind verified receipts. **Alternative rejected:** copying a full Ads Manager or allowing chat to launch an open-ended campaign. The first exposes provider complexity before company judgment; the second hides custody, special-category risk, maximum spend, and the difference between provider activity and business outcome.

### Company media surface

**What it is:** one thin company-level request and review surface for images and video. A request creates an ordinary owned task under the existing employee, project, budget, and runtime contracts; the finished image or video appears only when the employee attaches a real artifact or registers an artifact work product. **Reason:** generation is company work, not a special source of truth. The board needs one accountable owner, one inspectable brief, one cost boundary, and one durable output receipt regardless of which authorized tool or model produced it. **Trade-off settled:** the first surface does not manage provider credentials, invent another scheduler, or promise an asset synchronously. It can wake the assigned employee, who must use only capabilities already authorized for that employee and return `BLOCKED` when the required tool, credential, or budget is absent. **Alternative rejected:** decorative Image/Video buttons that fabricate success, a new provider-specific media database, or automatic publication. They respectively create theater, duplicate Tasks and Artifacts, or collapse generation and external communication into one unsafe action.

### Company stack surface

**What it is:** one company-level portable infrastructure control for a private GitHub repository, Neon database, Vercel project, exact credential custody, a fixed initial application plan, one exact source commit, owner exit links, board-only expiring database snapshots, and append-only receipts, plus one compact Mission Control glance. The Stack board renders Idea → Source → Production → Health as four independent cells; no later state upgrades an earlier claim. The snapshot card keeps export state, size, checksum, tool version, expiry, download, and early deletion on one causal line. **Reason:** “the company can build while I sleep” is incomplete unless its source, data, hosting, authority, partial failures, and practical exit path remain visible and owned by the founder. **Trade-off settled:** V1 chooses one opinionated web stack and one ten-file `summon-next-company` template. `ready_for_build` proves infrastructure; `source_ready` proves an exact commit; deployment and health remain Company Website receipts. Snapshot creation is read-only and restore stays outside Summon because export convenience does not imply destructive database authority. **Alternative rejected:** Polsia-style platform-owned infrastructure, a generic cloud console, a magical export-and-restore button, or a single green “done” badge. They respectively make convenience depend on lock-in, multiply configuration before evidence, hide a destructive boundary, or erase causality.

### Company website version-control surface

**What it is:** one compact list of immutable provider-reported production builds beside the existing deployment, domain, health, authority, and receipt chain. Current and provider-eligible rollback states are explicit; every row retains its exact deployment identity and safe provider URL. Instant Rollback, Redeploy Current, and Promote are separate destructive-colored, typed-confirmation board dialogs: rollback reroutes traffic to a previously served build, redeploy creates a new build from the exact current deployment, and promote sends a ready build to production while restoring automatic domain assignment after rollback. **Reason:** recovery is credible only when the founder can distinguish the current build from an eligible earlier or staged build and understand whether provider work is routing an immutable artifact or creating a new one. **Trade-off settled:** the board receives the complete rollback-to-recovery loop while arbitrary alias management remains outside the first surface. **Alternative rejected:** a generic history timeline, rebuilding an old commit while calling it rollback, or one ambiguous “retry deployment” button. ### Company mobile-build surface

**What it is:** one Stack-embedded, four-stage control for a company-owned Expo app: fix the idea/customer/first action and publish the versioned 13-file Expo SDK 57 starter to the exact private repository; build the generated commit through exact robot-token authority; authenticate Expo's signed Build event into a provider-owned artifact/install link; then, for a signed production `.aab` or `.ipa`, dispatch one governed submission to Google Play internal Draft or App Store Connect/TestFlight. ### Company AI-gateway surface

## The token layer (where visual values live)

The single token source is **`ui/src/index.css`** (Tailwind v4; there is no tailwind config file - tokens are CSS custom properties consumed via `@theme`). Do NOT create a parallel token source such as `ui/src/tokens/` - that would produce two sources of truth. If index.css grows unwieldy, extracted values may live in a `tokens.css` **imported by index.css** so the pipeline still has one root.

Tailwind v4 gotcha: `@theme inline` bakes literal values at build time. Any token that must be runtime-tunable (theme editor, dark mode overrides) must be defined in a NON-inline block.

Existing tiers already in index.css (~80+ tokens) - extraction maps to these on **exact value match** before minting anything new:

1. **Semantic tier** - shadcn core set: `--background`, `--foreground`, `--card`, `--primary`, `--secondary`, `--muted`, `--accent`, `--destructive`, `--border`, `--input`, `--ring`, `--sidebar-*`, `--chart-1..5` (OKLCH, light/dark overrides).
2. **Brand tier** - agent gradients `--agent-1a/1b..10a/10b` (fixed hex) and status hues `--status-task-*` / `--status-agent-*` (WCAG-tuned; see inline comments).
3. **Domain tier** - match-chip tokens `--chip-match-*`, annotation highlights `--paperclip-doc-annotation-highlight-*`, plus motion/typography tokens.

## Principles

1. **One way to say each thing.** One component per job. One Button, one Card, one Badge, one Table, one EmptyState. Variants are props, not new components. Before creating a component, prove no existing one covers the job.
2. **Tokens are the only source of visual values.** All color, spacing, radius, type size/weight, shadow, and motion values come from the token layer. No hex, no raw px, no ad-hoc Tailwind arbitrary values (`p-[13px]`) in components. If a needed value doesn't exist, add a token - don't inline it. Tailwind palette classes (`bg-red-500`, `text-zinc-400`, etc.) ARE hardcoded values in spirit: they name a literal color, not a semantic role. They are in-scope debt scheduled for a dedicated future run (Run 4, cluster-by-cluster mapping to semantic tokens per doc/design/DECISION-SHEET.md B2) and are not currently gated by check-token-gates. Exception (doc/design/DECISION-SHEET.md B1 user ruling): first-party intentional one-off decoration on demo/UX-lab surfaces stays inline and allowlisted rather than minted as singleton tokens.
3. **Spacing routes through tokens; the scale comes later.** During simplification, extract every spacing and radius value verbatim into tokens - do not normalize, round, or invent a scale. The final scale is a design decision made by a human after reviewing the token audit. Structural rules apply now: vertical rhythm within a container uses one gap value, not per-element margins, and siblings never carry both margin and gap.
4. **Hierarchy through structure, not decoration.** Prefer position, size, and weight over borders, backgrounds, and dividers. Every border, divider, and background fill must justify itself; when in doubt, remove it. A screen should survive the removal of one visual layer.
5. **Status is systematic.** States like running / paused / blocked / awaiting-approval / over-budget map to a single semantic status token set used identically everywhere (badge, row, chart, log). An operator learns the vocabulary once.
6. **Machine values look machine-made.** IDs, costs, token counts, timestamps, and log output use the monospace token and consistent formatting helpers. Never format these ad hoc per screen.
7. **Words are part of the system.** One name per concept across the entire UI - the canonical term is *task* (never *issue* or *ticket* in copy, labels, or empty states). Buttons name the action ("Approve hire," not "Submit"). Errors say what happened and what to do. Empty states say what to do first. **Note:** enforcing the task rename is a visible change and is explicitly OUT of the zero-visual-change extraction run; it happens in its own follow-up run.
8. **Agent-modifiable by design.** The system must be changeable via instructions: single token source, lint rules that enforce it, and this document kept current. A correct change should be expressible as "edit tokens + run checks," not "visit 40 files."

## Enforcement (what "compliant" means for the extraction run)

- **Zero visual change is proven, not promised:** Storybook visual snapshots are baselined before any refactor, and all snapshots match baseline after it. A change that alters rendered output must be intentional and human-approved.
- **Baseline scope for Run 1:** the shared primitives in `ui/src/components/ui/` (each gets a story if missing - there are only ~24) plus the ~46 existing stories under `ui/storybook/stories/`. Do NOT attempt a story for every feature component (~277) in this run; full coverage is a later effort.
- Mechanical rewrites (value extraction, renames) are done via committed codemod scripts in `scripts/`, not hand-edits - reviewable once, repeatable forever.
- Token layer is the single source (`ui/src/index.css`, per above) consumed via CSS variables / Tailwind theme - never values copied into components.
- Lint/grep gates pass: zero hardcoded hex values, zero arbitrary spacing values, zero raw font-size declarations in `ui/src/components/**` and `ui/src/pages/**` outside the token layer and a documented allowlist (third-party overrides, intentional opt-outs commented inline).
- `pnpm build`, `pnpm typecheck`, and `pnpm build-storybook` pass.
- AGENTS.md links here and states the token-only rule.

Aspirational (NOT gating this run): no duplicate components; every component has exactly one story covering its variants; all UI copy says "task".

## Out of scope (do not do during simplification)

No visual redesign, no new colors or typefaces, no layout restructuring, no new dependencies beyond snapshot tooling, no component consolidation/merges (audit + recommend only), no copy renames, no changes to server code or app logic. Simplification means fewer parts, same product.

### Portfolio budget guardrail surface

**What it is:** one financial-governance line that keeps company and employee ceilings causally aligned. A new Aether company starts in manual mode with an $80 monthly company ceiling equal to the eight proposed $10 employee ceilings. The formation decision shows the company hard stop beside the employee-cap total. ### Portfolio public-availability diagnosis

**What it is:** public reachability is a first-class company outcome, not merely scanner plumbing. A stable hostname-not-found result becomes a 0/100 `Public availability` scorecard, one highest-impact reliability finding, and one deterministic read-only Claude prompt derived from the retained evidence run. The prompt states what the cure is and is not: inspect repository-owned configuration, prepare the smallest correction, stop at domain, DNS, hosting, deployment, publication, spend, and communication boundaries, then require a newer successful public diagnosis as proof. A timeout, temporary resolver failure, TLS ambiguity, or other transport uncertainty remains `scan_failed`; it never becomes a scored finding or a false cure. **Reason:** a company that customers cannot reach has a clear binding constraint even though deeper page checks are impossible. Calling stable DNS absence “lost evidence” hides the most important error and prevents the promised improvement prompt. **Trade-off settled:** the zero score is intentionally severe but applies only to stable name-resolution evidence; every ambiguous failure fails closed. The prompt is virtual and evidence-derived, so reading the portfolio does not fabricate or rewrite a Lightmark artifact. **Alternative rejected:** treating every network exception as zero, treating DNS absence as merely unavailable, or silently changing owner infrastructure. Those choices respectively turn transient faults into false diagnoses, strand the company without an improvement path, or exceed board authority.

Those choices respectively deform the portfolio, erase real beneficiary value, or make classification non-deterministic.
